# Architecture

```
apps/api       Rails 8 API-only, MySQL 8.4          data plane (/v1) + sandbox control plane (/sandbox)
apps/mcp       TypeScript, official MCP SDK, stdio  a client of /v1 only
apps/console   React + TypeScript (Vite)            one screen; calls /sandbox through the dev proxy and /v1 with the key

curl ──────────┐
console ───────┼──> /v1/*  (API key, permissions, Idempotency-Key, request log) ──> MySQL
MCP server ────┘
console ──────────> /sandbox/*  (bootstrap secret, added by the Vite proxy, never sent to the browser)
```

## Domain

A sandbox owns a fictional organization: facilities with an IANA time zone and opening hours, courts with an hourly rate, and players. Keys belong to one sandbox; every resource outside it returns 404. Keys look like `bl_test_<lookup>_<secret>`; only a SHA-256 digest of the secret is stored, and the full key is shown once.

## Time

Availability takes a facility-local date. Every slot and every mutation uses RFC 3339 instants with an offset, and the database stores UTC. Slots are generated by walking real instants from opening to closing in 30 minute steps, so on the day clocks fall back the repeated hour appears twice with different offsets and no instant repeats. Naked local times are rejected.

## Holds

Creating a hold runs at READ COMMITTED and locks the key row, then the court row (`SELECT ... FOR UPDATE`), always in that order. With both locks held it counts the key's active holds (limit 3) and checks for an overlapping active hold or confirmed booking on the half-open window `[starts_at, ends_at)`. Expiry is lazy: a hold whose `expires_at` has passed is expired everywhere, with no background job.

## Preview and confirm

Preview issues a single-use token bound to the hold, the customer and the price, valid for 5 minutes or until the hold expires. Confirm locks the hold row, then re-checks the token (unused, unexpired, issued to this key), the hold (still active), the binding (same customer and price) and overlap, and only then marks the token used, converts the hold and inserts the booking. A unique index on `bookings.hold_id` is a second line of defence.

## Idempotency

Every mutation needs an `Idempotency-Key`. The server first claims the key by inserting an `in_progress` row under a unique index on (key id, Idempotency-Key), before doing any work. The work and the stored response are committed in the same transaction. A repeat with the same method, path, query and body replays the stored status and body; a different request gets 409 `idempotency_key_reused`; a repeat while the first is running gets 409 `idempotency_in_progress`. Outcomes that ran, including 4xx, are stored; unexpected 5xx are not, so a retry can run again.

## Request log

Every authenticated `/v1` request is logged with method, path, status, error code, duration, whether it was a replay, and the client (from `X-Client` or a curl User-Agent). The console polls it every 2 seconds.
